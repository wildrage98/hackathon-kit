# plan-verify

시간 제한이 있는 개발 과제를 **계획 → 구현 → 검증** 루프로 진행한다.
사용자가 시간을 관리한다. 네가 시간을 재지 않는다.

## 단계 1 — 계획 (코드 작성 금지)
1. `README.md`, 과제 안내, `docs/QUESTIONS.md`의 "확정 기준 메모"를 읽는다.
2. `docs/PLAN.md`를 채운다. 비어 있는 확정 기준이 있으면 코드를 쓰지 말고 사용자에게 "담당자에게 이 질문을 하세요"라고 목록으로 돌려준다.
3. 개발 순서 표(7번)에 각 단계의 **실행으로 확인 가능한 완료 기준**을 적는다.
4. 사용자가 "계획 승인"이라고 하기 전까지 구현으로 넘어가지 않는다.

## 단계 2 — 최소 실행본
1. 입력 로드 → 핵심 로직 1개 → 결과 출력이 한 명령으로 도는 뼈대를 먼저 만든다.
2. 만들자마자 실행한다: `tools/run_and_log.sh run <명령>`.
3. 돌아가면 `docs/DECISIONS.md`에 뼈대 설계 결정을 한 줄 적는다.

## 단계 3 — 기능 추가 (한 번에 하나)
각 기능마다:
1. 무엇을 추가하는지 한 문장
2. 구현
3. `tools/run_and_log.sh <태그> <명령>`으로 실행 확인
4. 실패하면 고친다. 세 번 실패하면 사용자에게 범위 축소를 제안한다.
5. 판단 로직을 넣을 때는 근거 출력을 반드시 같이 넣는다.

## 단계 4 — 검증
1. 합성 데이터에 **이상 케이스를 의도적으로 심은** 테스트 입력을 만든다 (위치·값을 `tests/`에 명시).
2. 기대 결과를 먼저 적고, 실행 후 비교한다.
3. `docs/VERIFICATION.md`에 입력·기대·실제·로그 경로를 적는다.
4. 실행하지 않은 항목은 "미검증"으로 적는다. 통과했다고 쓰지 않는다.

## 단계 5 — 정리
1. `README.md`: 설치·실행·결과 확인 순서, 입력 위치, 포트, 미구현 항목
2. `docs/DECISIONS.md`에 "AI 활용" 섹션 채우기: 네가 만든 것 중 사용자가 검토하지 않은 파일·함수 목록
3. `docs/SUBMIT_CHECK.md` 순서로 점검

## 응답 형식
- 단계 번호와 지금 하는 일을 첫 줄에 쓴다.
- 코드 설명은 생략하고 파일 경로·실행 명령·확인 결과만 쓴다.
