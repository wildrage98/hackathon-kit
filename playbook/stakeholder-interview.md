# 인터뷰

3~5개 묶음. 답은 바로 `docs/QUESTIONS.md` 표. README에 있는 건 묻지 않음.

## 1. 묶음 1 (0~8분)
```
안녕하세요, 개발을 맡은 OOO입니다. 시작 전에 몇 가지 확인드립니다.
1) 이 결과물을 실제로 쓰는 분은 누구이고, 언제 어떻게 보나요?
2) 지금은 이 일을 어떻게 처리하고 계신가요? 가장 큰 불편은요?
3) 최근에 실제로 문제가 됐던 사례 하나만 구체적으로 들려주실 수 있을까요?
4) 반드시 되어야 하는 것 3가지와, 되면 좋은 것을 나눠주세요.
5) 명시적으로 하지 않아도 되는 것은요? (실설비 연결, 실시간, ML, 로그인 등)
```

## 2. 묶음 2 (8~15분, profile 결과 들고)
```
데이터를 훑어봤습니다. 확인 부탁드립니다.
1) 컬럼 X의 단위와 정상 범위는요? (관측 min~max a~b)
2) state 값 중 판정에서 제외할 상태가 있나요?
3) 결측 c%는 수집 실패인가요, 해당 없음인가요? '표시만 하고 판정 제외'로 처리해도 될까요?
4) 주기 d초 기준 몇 배 끊기면 '수신 장애'로 볼까요? 장애 자체를 경보로 볼까요?
5) 정상 기준을 수치로 주실 수 있나요? 없다면 제가 정상 구간 데이터로 제안 드리고 확정받겠습니다.
```
`profile.questions_from_profile()` 후보 참고.

## 3. 기준 없을 때
```
정상 기준이 문서로 없다고 하셨으니, 제가 다음과 같이 잡겠습니다:
- 설비별 RUN 상태 앞 1/3 구간을 기준으로 IQR 2배를 WARN, 4배를 CRIT로 제안합니다.
- 단발 초과는 확정하지 않고 2회 연속일 때 확정, 정상 1분(6샘플) 지속 시 해제.
이대로 진행해도 될까요? 다른 기준이 있으면 그 값으로 바꾸겠습니다.
```
답 → `config/rules.json` + AGREEMENT.

## 5. 체크인 (60, 120분)
```
중간 보고입니다. 현재 1) 2) 가 동작하고, 3)은 진행 중입니다.
확인 1개: (예: 중복 행의 값이 다를 때 어느 쪽을 믿을까요?)
남은 시간 고려해 4)는 '정책만 문서화'로 축소하려 합니다. 괜찮을까요?
```
